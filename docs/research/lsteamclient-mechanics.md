# How Proton's `lsteamclient` actually works — and the minimum subset for one achievement

**Scope:** the mechanics of Proton's `lsteamclient/` — the PE↔unix seam, the versioned-interface
code generator, struct-layout divergence, the callback return path — and which of it survives a
port to macOS/Mach-O. The CrossOver/bottle side of the problem is covered separately in
`crossover-bridge-surface.md`.

**Investigated:** 2026-08-03.

**Primary sources.** All Proton citations are against a checkout of
`ValveSoftware/Proton`, branch `proton_11.0`, at commit `0745bfbc4cf4` ("lsteamclient: Make struct
`networking_message` layout compatible between 32 and 64 bit", 2026-07-24). Wine citations are
against `wine-10.0` (the version CrossOver 25.1.1 ships) unless noted. Steamworks SDK citations are
against the copies vendored in `lsteamclient/steamworks_sdk_165/` — Proton vendors **105 SDK
versions**, `099u` through `165`, which is itself a load-bearing fact (§4).

---

## Summary (read this first)

1. **`lsteamclient` is not a "wrapper DLL". It is a Wine builtin DLL with a unixlib.** It ships as a
   pair: a PE side (`lsteamclient.dll`) and an ELF/Mach-O side (`lsteamclient.so`) built from the
   same source tree, talking over Wine's `__wine_unix_call` seam. The PE side contains **zero**
   Steam logic — it is pure marshalling. All real calls happen on the unix side against the native
   `steamclient.so`/`.dylib`.
2. **The seam is one function pointer and one integer.** `__wine_unix_call(handle, code, args)`
   where `handle` is the address of a `const unixlib_entry_t []` array inside the `.so`, `code` is
   an index into it, and `args` is a single packed struct. That's the whole ABI. There is no
   serialisation, no IPC, no thread hop.
3. **The `this` pointer never crosses as a pointer.** Every generated call passes
   `struct u_iface { UINT64 handle; }` — a bitness-independent 64-bit opaque handle to the *native*
   interface pointer. The PE-side object (`struct w_iface`) is a two-field shim: a fake MSVC vtable
   plus that handle.
4. **~10 000 thunks are generated by `gen_wrapper.py`** from the 105 vendored SDK header sets, using
   the **clang Python bindings**, parsing each SDK **four times** (`u32`/`u64`/`w32`/`w64`) so that
   struct layout is *measured*, never assumed.
5. **The struct-divergence problem has exactly one root cause**, and it is in Valve's own headers:
   `steamclientpublic.h:1148-1157` selects `VALVE_CALLBACK_PACK_SMALL` (`#pragma pack(4)`) on
   `__linux__ || __APPLE__ || __FreeBSD__` and `VALVE_CALLBACK_PACK_LARGE` (`#pragma pack(8)`)
   everywhere else, i.e. on Windows. **macOS is on the `PACK_SMALL` side, identical to Linux.** Every
   layout conclusion Proton reached for Linux transfers to macOS unchanged.
6. **For a single achievement round-trip, none of that matters.** `UserStatsReceived_t` (1101),
   `UserStatsStored_t` (1102) and `UserAchievementStored_t` (1103) are byte-identical on all four
   ABIs — Proton's generator classifies them as "unique" structs and emits **no conversion entries**
   for those callback IDs (§6.3). The minimum viable path needs **2 interfaces and ~8 methods** (§7).
7. **Building lsteamclient the Proton way requires a fully configured *and built* Wine tree**, not
   just headers: `make/rules-makedep.mk` grafts the module into Wine's own generated `Makefile` and
   runs Wine's `tools/makedep`. That is *not* how we should build ours (§3.3) — the runtime ABI is
   tiny and we can reimplement it, which the CrossOver research already established empirically.
8. **Proton's tree already contains a macOS branch** for locating the native library:
   `unixlib.cpp:738-746` loads `$STEAM_COMPAT_CLIENT_INSTALL_PATH/steamclient.dylib` under
   `#ifdef __APPLE__`. The design anticipates us.

## 1. The PE↔unix seam

### 1.1 What the ABI actually is

`include/wine/unixlib.h` (Wine 10.0) defines the entire contract. On the **unix** side
(`WINE_UNIX_LIB` defined):

```c
typedef UINT64 unixlib_handle_t;
typedef NTSTATUS (*unixlib_entry_t)( void *args );

extern DECLSPEC_EXPORT NTSTATUS __wine_unix_lib_init(void);
extern DECLSPEC_EXPORT const unixlib_entry_t __wine_unix_call_funcs[];
extern DECLSPEC_EXPORT const unixlib_entry_t __wine_unix_call_wow64_funcs[];
```

On the **PE** side:

```c
extern unixlib_handle_t __wine_unixlib_handle;
extern NTSTATUS (WINAPI *__wine_unix_call_dispatcher)( unixlib_handle_t, unsigned int, void * );
extern NTSTATUS WINAPI __wine_init_unix_call(void);

static inline NTSTATUS __wine_unix_call( unixlib_handle_t handle, unsigned int code, void *args )
{
    return __wine_unix_call_dispatcher( handle, code, args );
}

#define WINE_UNIX_CALL(code,args) __wine_unix_call( __wine_unixlib_handle, (code), (args) )
```

So: **an array of `NTSTATUS (*)(void*)`, indexed by an integer, taking one opaque argument pointer.**
Nothing else.

### 1.2 How the two halves find each other

Three steps, all in Wine, none of them in `lsteamclient`:

1. When ntdll's unix side maps a builtin PE dll it records the sibling `.so` path against the module:
   `load_builtin_unixlib(module, name)` — `dlls/ntdll/unix/virtual.c:674-690` (wine-10.0). The path is
   derived in `dlls/ntdll/unix/loader.c` by rewriting `foo.dll` → `<dll_path>/<arch>-unix/foo.so`
   and `dlopen`-ing candidates in order (loader.c:1324-1362).
2. `get_builtin_unix_funcs()` — `virtual.c:642-668` — lazily `dlopen(path, RTLD_NOW)`s it and does
   `dlsym(handle, "__wine_unix_call_funcs")` (or `"__wine_unix_call_wow64_funcs"`), returning the
   array address.
3. The PE side asks for it by image base:

   ```c
   NTSTATUS WINAPI __wine_init_unix_call(void)
   {
       return NtQueryVirtualMemory( GetCurrentProcess(), image_base(), MemoryWineUnixFuncs,
                                    &__wine_unixlib_handle, sizeof(__wine_unixlib_handle), NULL );
   }
   ```
   — `dlls/winecrt0/unix_lib.c:92-96`, dispatched at `virtual.c:5530-5542`.

   Note `__wine_init_unix_call` lives in **winecrt0**, not ntdll — it is statically linked into each
   builtin PE. `ntdll.spec:1744-1746` only exports `__wine_unix_call_dispatcher` and
   `__wine_unixlib_handle` as `extern -private` data symbols. The dispatcher is resolved lazily on
   first call via `RtlFindExportedRoutineByName` (`unix_lib.c:45-62`), so a module that never calls
   into unix pays nothing.

`lsteamclient` invokes exactly one line of this: `steamclient_main.c:68`, `__wine_init_unix_call()`
in `DLL_PROCESS_ATTACH`.

### 1.3 The wrapper Proton puts on top

`lsteamclient/unixlib.h:429-436`:

```c
NTSTATUS steamclient_call( unsigned int code, void *args, const char *name );

#define STEAMCLIENT_CALL( code, args )                                     \
    ({                                                                     \
        NTSTATUS status = steamclient_call( unix_ ## code, args, #code );  \
        assert( !status );                                                 \
        status;                                                            \
    })
```

and `steamclient_main.c:83-94`:

```c
NTSTATUS steamclient_call( unsigned int code, void *args, const char *name )
{
    NTSTATUS status = WINE_UNIX_CALL( code, args );
    if (status == STATUS_ACCESS_VIOLATION)
    {
        ERR( "Access violation in %s.\n", name );
        *(volatile int *)0xbeef |= 0;
    }
    ...
}
```

The deliberate null-deref on `STATUS_ACCESS_VIOLATION` is because a fault taken on the unix side
cannot be delivered to the PE-side SEH handler — Proton converts it into a PE-side fault so the
crash is attributable. **We will need the same trick or an equivalent**, because macOS Mach
exception handling has the same asymmetry.

### 1.4 wow64

Every entry point is generated twice. `unixlib_generated.cpp` emits two parallel arrays,
`__wine_unix_call_funcs[]` and `__wine_unix_call_wow64_funcs[]`, in the same order, and the second
set reads `wow64_*_params` structs where every pointer field is a `struct ptr32<T>` — a 32-bit slot
with assert-checked conversion operators (`steamclient_structs.h:42-62, 76-79`). The pattern is
mechanised by `STEAMCLIENT_UNIX_FUNC` / `LSTEAMCLIENT_UNIX_IMPL` (`unixlib.cpp:1285-1294`,
`unix_private.h:120-140`) which instantiate the same C++ template over both params types.

**We do not need this.** Our target is a win64 PE talking to an x86_64 unix side; there is no
bitness crossing. Dropping wow64 halves the generated surface.

## 2. The object model: `w_iface` / `u_iface`

`steamclient_private.h:31-40`:

```c
struct w_iface
{
    vtable_ptr *vtable;
    struct u_iface u_iface;
};

typedef struct w_iface *(*iface_constructor)( struct u_iface );
```

`steamclient_structs.h:97-104`:

```c
struct u_iface
{
    UINT64 handle;
#ifdef __cplusplus
    struct u_iface &operator=( const void* value ) { this->handle = (UINT_PTR)value; return *this; }
    template< typename T > operator T*() const { return (T*)(UINT_PTR)this->handle; }
#endif
};
```

That is the whole trick, and it is the single most reusable idea in the codebase:

- A PE-side interface object is **16 bytes**: a pointer to a hand-built MSVC-layout vtable, plus an
  opaque 64-bit handle to the native object.
- The handle is *always* 64 bits regardless of PE bitness, so the params structs have one layout.
- On the unix side the handle is cast straight back to a `struct u_ISteam*` — a C++ class with the
  same pure-virtual declarations in the same order as the native library's, so the compiler emits an
  ordinary Itanium-ABI virtual dispatch. `unix_private_generated.h` is 20 916 lines of exactly that:

  ```c
  struct u_ISteamUserStats_STEAMUSERSTATS_INTERFACE_VERSION013
  {
      virtual int8_t GetStat( const char *, int32_t * ) = 0;
      ...
      virtual int8_t SetAchievement( const char * ) = 0;
      virtual int8_t ClearAchievement( const char * ) = 0;
      virtual int8_t GetAchievementAndUnlockTime( const char *, int8_t *, uint32_t * ) = 0;
      virtual int8_t StoreStats(  ) = 0;
      ...
  };
  ```

  No `dlsym` per method, no manual vtable indexing — the C++ compiler reproduces the ABI.

### 2.1 Interface creation and caching

`CreateInterface` (`steamclient_main.c:388-396`) forwards the *version string* to the unix side,
gets back a `u_iface`, then calls `create_win_interface(name, u_iface)` (`:278-326`), which:

- looks up an existing `w_iface` for the same `(name, handle)` pair in a linked list under a critical
  section — **interface identity must be stable**, games compare pointers;
- otherwise calls `find_iface_constructor(name)` — a linear scan over a generated
  `{version_string, ctor}` table in `steamclient_generated.c:5+`, including `/* alias */` rows for
  binary-compatible undocumented versions;
- `ERR("Don't recognize interface name: %s")` on miss.

### 2.2 The `steamclient.dll` `.data` allocation hack

`steamclient_main.c:103-266` is worth reading before we design anything: some games (Mafia II is
named at `:218-219`) require the returned interface pointer *and its vtable* to live inside the
address range of the real `steamclient.dll` module. Proton locates the `.data` section of the loaded
`steamclient.dll` via `RtlImageNtHeader`, writes a magic word, and bump-allocates interface objects
and vtable copies out of it (`alloc_mem_for_iface`, `alloc_vtable`). Objects allocated this way are
deliberately **not cached** (`:304-310`) because the module can be reloaded at a different base.

This is a compatibility wart, not a mechanism — skip it in v1, but know it exists.

## 3. Vtable reproduction, and the build coupling

### 3.1 Fake MSVC vtables in inline asm

`cxx.h:30-53` (a CodeWeavers file, LGPL, originally by Piotr Caban):

```c
#ifdef _WIN64
#define VTABLE_ADD_FUNC(name) "\t.quad " THISCALL_NAME(name) "\n"
#define __ASM_VTABLE(name,funcs) \
    __asm__(".data\n" \
            "\t.balign 8\n" \
            "\t.quad " __ASM_NAME(#name "_rtti") "\n" \
            "\t.globl " __ASM_NAME(#name "_vtable") "\n" \
            __ASM_NAME(#name "_vtable") ":\n" \
            funcs "\n\t.text")
#endif
```

Note the RTTI locator slot immediately *before* the first method — required by the MSVC ABI so that
`dynamic_cast`/`typeid` inside a game doesn't fault. `DEFINE_RTTI_DATA0(winISteamUserStats_..., 0,
".?AVISteamUserStats@@")` supplies the mangled name; `init_rtti()` fixes up the RVA-based structures
at `DLL_PROCESS_ATTACH` (`steamclient_main.c:64-67`) because on x86_64 MSVC RTTI uses image-relative
addresses.

The generated tail of `winISteamUserStats.c` (around `:6330-6382`) is the canonical example:

```c
__ASM_BLOCK_BEGIN(winISteamUserStats_STEAMUSERSTATS_INTERFACE_VERSION013_vtables)
    __ASM_VTABLE(winISteamUserStats_STEAMUSERSTATS_INTERFACE_VERSION013,
        VTABLE_ADD_FUNC(..._GetStat_2)
        VTABLE_ADD_FUNC(..._GetStat)
        VTABLE_ADD_FUNC(..._SetStat_2)
        VTABLE_ADD_FUNC(..._SetStat)
        ...
        VTABLE_ADD_FUNC(..._SetAchievement)
        ...
```

**Read that ordering carefully.** The SDK header declares `GetStat(const char*, int32*)` *before*
`GetStat(const char*, float*)`, but the emitted vtable puts `GetStat_2` (the float overload) first.
That is the MSVC ABI rule: **members of the same overload set are laid out in reverse declaration
order**. `gen_wrapper.py` encodes it by sorting on `(x._index, -x._override)`. Itanium (clang/gcc) does
*not* do this, which is why the unix-side `u_` class keeps declaration order and the two orders are
allowed to differ. **If we hand-write vtables we must reproduce this or overloaded methods will be
silently swapped** — and `GetStat`/`SetStat` are exactly the methods a stats-using game touches.

### 3.2 Thiscall

`DEFINE_THISCALL_WRAPPER(name, stack_bytes)` emits a naked `pop eax; push ecx; push eax; jmp func`
trampoline **only on i386**; on every other architecture Wine defines it away
(`include/wine/asm.h:218-224`):

```c
# define DEFINE_THISCALL_WRAPPER(func,args) /* nothing */
# define THISCALL(func) func
# define THISCALL_NAME(func) __ASM_NAME(#func)
```

Because we are targeting win64 only, **the entire thiscall apparatus disappears** — `__thiscall` with
`this` in RCX is just the normal x86_64 Windows calling convention with a leading pointer argument.

### 3.3 Build-time coupling to Wine — does it need the tree or just headers?

**It needs a configured *and partially built* Wine source tree.** From `Makefile.in:418-423`:

```make
LSTEAMCLIENT_DEPENDS = wine
$(eval $(call rules-source,lsteamclient,$(SRCDIR)/lsteamclient))
$(eval $(call rules-makedep,lsteamclient,i386))
$(eval $(call rules-makedep,lsteamclient,x86_64))
$(eval $(call rules-makedep,lsteamclient,aarch64))
```

`make/rules-makedep.mk` shows what `rules-makedep` does: it depends on `$(OBJ)/.wine-$(HOST_ARCH)-tools`,
then **`sed`-rewrites Wine's own generated top-level `Makefile`** (substituting `SUBDIRS`, `objdir`,
`toolsdir`, per-arch `CFLAGS`/`CXXFLAGS`/`LDFLAGS`, and pinning
`UNIX_LIBS = $(WINE_$(3)_LIBDIR)/wine/$(3)-unix/ntdll.so`), and finally runs
**`$(WINE_$(HOST_ARCH)_OBJ)/tools/makedep`** inside the object dir. `lsteamclient/Makefile.in` is a
Wine-style module makefile (`MODULE = lsteamclient.dll`, `UNIXLIB = lsteamclient.so`,
`IMPORTS = user32 ws2_32`), and the `#pragma makedep unix` markers at the top of every unix-side
`.cpp` are what tell `makedep` to compile that TU with `-DWINE_UNIX_LIB` into the `.so` rather than
the PE.

So Proton's build is: *build Wine → graft lsteamclient in as if it were a Wine dll → let Wine's build
system produce both halves.* It also builds for **aarch64**, moving the output from
`arm64ec-windows/` to `aarch64-windows/` afterwards.

**Implication for us.** We do not have — and should not want — a Proton-style Wine build. But we do
not need one: the *runtime* contract (§1.1) is two exported symbol arrays plus the "Wine builtin DLL"
DOS-stub marker, and `crossover-bridge-surface.md` established empirically that CrossOver 25.1.1's
shipped `ntdll` implements all of it and that `wineloader` carries
`com.apple.security.cs.disable-library-validation`, so an unsigned third-party `.so` can be loaded.
We build our PE with mingw-w64 and our unix side with clang, and hand-roll the two symbol arrays.
What we *cannot* copy is the `Makefile.in`/`makedep` machinery, `DEFINE_THISCALL_WRAPPER`,
`__ASM_VTABLE`, `WINE_DEFAULT_DEBUG_CHANNEL`, `wine/list.h` — those are Wine-internal and would have
to be vendored or replaced. All are small.

## 4. The generator

`gen_wrapper.py` (1828 lines) + `gen.sh`. Run from `lsteamclient/`; `gen.sh` deletes the generated
files and re-runs it. Outputs are **committed** to the repo, so the generator is a build-time tool for
Valve, not for downstream builders.

### 4.1 Input

- `SDK_VERSIONS` (lines 13-105): a **hardcoded** list of 105 version strings, `"165"` down to
  `"099u"`, each mapping to a vendored `steamworks_sdk_<ver>/` directory. Not discovered from disk.
- `SDK_SOURCES` (109-179): 17 header filenames → the interface class names expected in each.
- Interface *versions* are discovered by regexing every file in each SDK dir for
  `^#define\s*(?P<name>STEAM(?:\w*)_VERSION(?:\w*))\s*"(?P<version>.*)"` (line 325) — i.e. from
  `#define STEAMUSERSTATS_INTERFACE_VERSION "STEAMUSERSTATS_INTERFACE_VERSION013"`.
- Parsing is `clang.cindex` (line 8) over a synthesised in-memory TU, **four times per SDK version**
  (`ABIS = ['u32','u64','w32','w64']`, line 107) — 420 translation units, run through a
  `ThreadPoolExecutor`. The `w*` parses add `-D_WIN32 -U__linux__ -fms-extensions -mms-bitfields`
  (1290-1296). `assert len(diagnostics) == 0` — any warning aborts.

This is the part that makes the whole design work: **layout is measured by a real compiler for both
ABIs, never hand-derived.**

### 4.2 Output, per method

For `ISteamUserStats::SetAchievement` on `STEAMUSERSTATS_INTERFACE_VERSION013`:

**Params struct** (`unixlib_generated.h`, inside `pshpack1.h`/`poppack.h`) —
`u_iface` first, `_ret` second, then arguments:

```c
struct ISteamUserStats_STEAMUSERSTATS_INTERFACE_VERSION013_SetAchievement_params
{
    struct u_iface u_iface;
    int8_t _ret;
    const char *pchName;
};
```

**PE-side thunk** (`winISteamUserStats.c:5806-5817`):

```c
int8_t __thiscall winISteamUserStats_STEAMUSERSTATS_INTERFACE_VERSION013_SetAchievement(struct w_iface *_this, const char *pchName)
{
    struct ISteamUserStats_STEAMUSERSTATS_INTERFACE_VERSION013_SetAchievement_params params =
    {
        .u_iface = _this->u_iface,
        .pchName = pchName,
    };
    TRACE("%p\n", _this);
    IsBadStringPtrA(pchName, -1);
    STEAMCLIENT_CALL( ISteamUserStats_STEAMUSERSTATS_INTERFACE_VERSION013_SetAchievement, &params );
    return params._ret;
}
```

The `IsBadStringPtrA` is not a validity check — it is a deliberate **pre-touch**. `PRETOUCH_TYPES`
(gen_wrapper.py:471-473) emits it for every `const char *` because DRM'd games keep arguments in
encrypted pages whose VEH-based decryption handler only runs if the fault is taken on the PE side.
A fault taken inside the unix `.so` would not be routed to the game's handler. **This will bite us
identically on macOS** — a page fault inside our `.dylib`/`.so` is a Mach exception, not a Windows
VEH — so keep the pre-touch.

**Unix-side dispatcher** (`cppISteamUserStats_STEAMUSERSTATS_INTERFACE_VERSION013.cpp:116-122`):

```c
NTSTATUS ISteamUserStats_STEAMUSERSTATS_INTERFACE_VERSION013_SetAchievement( void *args )
{
    struct ISteamUserStats_..._SetAchievement_params *params = (struct ISteamUserStats_..._SetAchievement_params *)args;
    struct u_ISteamUserStats_..._VERSION013 *iface = (struct u_ISteamUserStats_..._VERSION013 *)params->u_iface;
    params->_ret = iface->SetAchievement( params->pchName );
    return 0;
}
```

**Enum + table entry**: `unix_ISteamUserStats_STEAMUSERSTATS_INTERFACE_VERSION013_SetAchievement` in
`enum unix_funcs` (`unixlib_generated.h:104885`) and the function name at the matching index in
`__wine_unix_call_funcs[]`. The 18 hand-written entries (`UNIX_FUNCS`, gen_wrapper.py:244-262) come
first, then every generated method in `sorted(all_classes.items())` order.

The generator's escape hatches, all near the top of the file — this is the honest inventory of what
"can't be generated":

`abis["w64"] != abis["u64"]` compares object identity — `Struct` defines no `__eq__` — so it is
always true and the callback table is a harmless superset.

## 5. Struct layout divergence

### 5.1 Where it comes from

`steamworks_sdk_165/steamclientpublic.h:1148-1157`:

```c
#if defined(__linux__) || defined(__APPLE__) || defined(__FreeBSD__)
// The 32-bit version of gcc has the alignment requirement for uint64 and double set to
// 4 ... The 64-bit version of gcc has the alignment requirement for these types set to
// 8 ... The 64-bit structure packing has to match the 32-bit structure packing for each platform.
#define VALVE_CALLBACK_PACK_SMALL
#else
#define VALVE_CALLBACK_PACK_LARGE
#endif
```

`PACK_SMALL` → `#pragma pack(push, 4)` around every callback struct; `PACK_LARGE` → `pack(8)`. Valve
even asserts it: `sizeof(ValvePackingSentinel_t) == 24` vs `== 32` (`:1177-1183`).

**This is the entire problem, and macOS is on Linux's side of it.** Everything Proton computed for
`u32`/`u64` applies verbatim to a macOS `steamclient.dylib`.

### 5.2 How Proton handles it

Not with `#pragma pack` guesswork — by re-emitting each struct with clang-measured alignment and
**explicit padding members**, then asserting the result at compile time. From
`steamclient_structs_generated.h:4032`:

```c
#pragma pack( push, 8 )
struct w64_FileDetailsResult_t
{
    uint32_t m_eResult;
    uint8_t __pad_4[4];
    uint64_t m_ulFileSize;
    W64_ARRAY(uint8_t, 20, m_FileSHA);
    uint32_t m_unFlags;
#ifdef __cplusplus
    operator u64_FileDetailsResult_t() const;
#endif
};
#pragma pack( pop )
#pragma pack( push, 4 )
struct u64_FileDetailsResult_t { uint32_t m_eResult; uint64_t m_ulFileSize; /* no hole */ ... };
```

Naming convention: `w` = Windows/MSVC layout, `u` = unix/Itanium layout, `32`/`64` = bitness. Bare
`u_`/`w_` are `#ifdef`-selected aliases for the host bitness
(`steamclient_structs_generated.h:1628-1635`). When a pair needs no conversion, the `u` name is
`typedef`'d directly onto the `w` struct so **no copy is generated at all**.

Conversion, where needed, is a C++ conversion operator emitted into `unixlib_generated.cpp`, and the
unix dispatcher just leans on implicit conversion:

```c
u_SteamUGCDetails_t_160 u_pDetails = *params->pDetails;
params->_ret = iface->GetQueryUGCResult( params->handle, params->index, &u_pDetails );
*params->pDetails = u_pDetails;
```

Every struct is guarded by generated `C_ASSERT`s compiled on **both** sides
(`unixlib_generated.cpp`, e.g. `:14838-14848`):

```c
C_ASSERT( sizeof(UserAchievementStored_t) >= 152 );
C_ASSERT( offsetof(UserAchievementStored_t, m_nGameID) == 0 );
C_ASSERT( offsetof(UserAchievementStored_t, m_bGroupAchievement) == 8 );
C_ASSERT( offsetof(UserAchievementStored_t, m_rgchAchievementName) == 9 );
C_ASSERT( offsetof(UserAchievementStored_t, m_nCurProgress) == 140 );
C_ASSERT( offsetof(UserAchievementStored_t, m_nMaxProgress) == 144 );
```

**Copy this idea wholesale.** It is cheap, it turns an entire class of silent memory corruption into
a compile error, and it needs no generator.

### 5.3 Per-interface-version size mismatch

Versioning is handled by *size*, not by version string. `classify_struct()` (1336-1380) walks SDK
versions newest→oldest and mints a suffixed name (`UserStatsReceived_t_102x`,
`LeaderboardScoreUploaded_t_123`) only when the measured layout actually changed. Structs identical
across all four ABIs *and* all 105 SDK versions become "unique" and are emitted **once, unprefixed**.

At runtime the disambiguator is the callback length the game asks for — see §6.2.

## 6. The callback and call-result return path

There are two independent return channels. Getting this distinction right matters more than anything
else in this document.

### 6.1 Channel A — the Steam callback pipe (`Steam_BGetCallback`)

This is how *native Steam callbacks* reach the game. Crucially, **`lsteamclient` does not implement
`SteamAPI_RunCallbacks`.** That function lives in the game's own `steam_api64.dll` — Valve's
unmodified Windows redistributable, running as PE code inside the prefix. `SteamAPI_RunCallbacks`
drives the loop documented in `steam_api.h:175-205`:

```c
HSteamPipe hSteamPipe = SteamAPI_GetHSteamPipe();
SteamAPI_ManualDispatch_RunFrame( hSteamPipe )
CallbackMsg_t callback;
while ( SteamAPI_ManualDispatch_GetNextCallback( hSteamPipe, &callback ) )
{
    if ( callback.m_iCallback == SteamAPICallCompleted_t::k_iCallback ) { ... }
    else { /* dispatch to registered CCallbackBase */ }
    SteamAPI_ManualDispatch_FreeLastCallback( hSteamPipe );
}
```

Underneath, `steam_api64.dll` calls the flat C exports of `steamclient64.dll` — which is us. Hence
`lsteamclient.spec`:

```
8  cdecl Steam_BGetCallback(long ptr ptr)
15 cdecl Steam_FreeLastCallback(long)
30 cdecl Steam_GetAPICallResult(long int64 ptr long long ptr)
6  cdecl CreateInterface(ptr ptr)
35 cdecl Steam_ReleaseThreadLocalMemory(long)
```

`Steam_BGetCallback` is a **two-phase** operation (`steamclient_main.c:496-554` + `unixlib.cpp:330-384`):

1. `steamclient_Steam_BGetCallback` calls the native `Steam_BGetCallback`, gets a `u_CallbackMsg_t`,
   heap-copies it on the unix side, fills only the PE-visible header fields
   (`m_hSteamUser`, `m_iCallback`) and — critically — **rewrites `m_cubParam` to the Windows-side
   length** via `callback_len_utow()`. It returns the unix `u_msg` pointer to the PE side as an
   opaque `cookie`.
2. The PE side then allocates a `HeapAlloc` buffer of that Windows length, stores it in
   `win_msg->m_pubParam`, and issues a *second* unix call, `steamclient_callback_message_receive`,
   which runs the actual layout conversion into the PE-side buffer and frees the unix copy.

The reason for the split is that the PE side owns the destination buffer (games call
`Steam_FreeLastCallback` and expect PE heap semantics) but only the unix side knows the size mapping.

`SteamAPICallCompleted_t` (id 703) gets special treatment at `unixlib.cpp:363-380`: its *payload* is
itself a callback id + length, so the length field inside it must be translated too.

There is also a hack in the middle of the pump: callback `0x14b` (`GameOverlayActivated_t`) triggers
synthetic `keybd_event` key-ups for shift/tab and swallows spurious deactivations
(`steamclient_main.c:528-550`).

### 6.2 Length-keyed struct version resolution

`struct callback_def` (`unix_private.h:62-69`):

```c
struct callback_def
{
    int id;
    int sdkver;
    int w_callback_len;
    int u_callback_len;
    void (*conv_w_from_u)(void *dst, const void *src);
};
extern const struct callback_def callback_data[];
extern const struct callback_def wow64_callback_data[];
```

Generated rows look like (`unixlib_generated.cpp:28440`):

```c
{ 152, 165, 24, 16, []( void *d, const void *s ){ *(w32_MicroTxnAuthorizationResponse_t_123 *)d = *(const u32_MicroTxnAuthorizationResponse_t_123 *)s; } },
```

Sorted by id, binary-searched by `find_first_callback_def_by_id` (`unixlib.cpp:1186-1209`), then
scanned linearly among rows with the same id. Three consumers:

- `callback_len_utow(id, u_len)` → the PE-side length for a given native length (`:31-47`);
- `alloc_callback_wtou(id, w_buf, &len)` → picks the row whose `w_callback_len` matches the caller's
  buffer (falling back to the largest that fits, with `ERR`/`WARN`), rewrites `len` to the unix
  length and `malloc`s it (`:1211-1241`);
- `convert_callback_utow(...)` → invokes `conv_w_from_u`, or `memcpy` if there is no row
  (`:1243-1283`).

**The disambiguator is the buffer length the game passes, not any version string.** That is how one
binary serves games built against any of 105 SDKs. It is a genuinely good design and we should copy
it verbatim.

### 6.3 Call results

`Steam_GetAPICallResult` (`steamclient_main.c:556-574` → `unixlib.cpp:393-411`) is the simple case,
because the *caller* supplies both the buffer and the expected callback id:

```c
int u_callback_len = params->w_callback_len;
void *u_callback = alloc_callback_wtou( params->id, params->w_callback, &u_callback_len, false );
params->_ret = p_Steam_GetAPICallResult( params->pipe, params->call, u_callback, u_callback_len,
                                         params->id, params->failed );
if (params->_ret && u_callback != params->w_callback)
{
    convert_callback_utow( params->id, u_callback, u_callback_len, params->w_callback, params->w_callback_len, false );
    free( u_callback );
}
```

Note `alloc_callback_wtou` returns the *original* pointer when no conversion is needed, and the code
tests pointer identity to decide whether to convert — no conversion, no allocation, no copy.

The `CCallbackBase` vtable is **never touched by `lsteamclient`**. It lives entirely in the game's PE
address space; `steam_api64.dll` invokes `Run(void*)` / `Run(void*, bool, SteamAPICall_t)` /
`GetCallbackSizeBytes()` on it (`steam_api_common.h:138-157`). Confirming this, the generator lists
`CCallbackBase` in `EXEMPT_STRUCTS` with the comment `# not actually used`. `GetCallbackSizeBytes()`
returning the *Windows* `sizeof(P)` is precisely the value that flows into `Steam_GetAPICallResult`'s
`cubCallback` and therefore into `alloc_callback_wtou`'s length lookup — which is why the
length-keyed table works.

### 6.4 Channel B — unix→PE upcalls (the deferred callback queue)

Separate machinery, for the handful of APIs where the game hands *its own function pointer* to Steam:
`SetWarningMessageHook`, `SetDebugOutputFunction`, `ISteamMatchmakingServers` response interfaces,
etc. A native thread cannot call a PE function pointer directly — wrong calling convention, wrong
stack, wrong TEB. So:

- The unix side registers its *own* callback (`u_steam_api_warning_message_hook`, `unixlib.cpp:204-223`)
  and remembers the PE pointer.
- When it fires, it `calloc`s a `struct callback_entry`, copies the arguments **by value** into a
  flat tagged union (`struct callback`, `unixlib.h:56-169`) and appends it to a global list under
  `pthread_mutex_t callbacks_lock`.
- On the PE side, `execute_pending_callbacks()` (`steamclient_main.c:398-478`) — called at the top
  and bottom of every `Steam_BGetCallback` — drains the queue via the `steamclient_next_callback`
  unix call and dispatches by `enum callback_type`, including a macro-generated set of
  "call vtable slot N with 0/1/2 `intptr_t` args" cases (`CALL_IFACE_VTABLE_*`) implemented with
  `CALL_VTBL_FUNC`.

Every function-pointer field in that union is padded to `UINT64` via an anonymous union with
`UINT64 __pad` so the struct has one layout in both bitnesses.

**Design consequence: upcalls are deferred to the game's own callback pump.** They never run on a
Steam thread. We should adopt this unconditionally — it is the only sane way to cross the boundary
in that direction, and none of it is on the achievement path anyway.

## 7. The critical path: `SteamAPI_Init` → `SetAchievement` → unlock

### 7.1 Bootstrapping

1. Wine's `wine.inf` (Valve fork, `loader/wine.inf.in:1400-1407`, section `[SteamClient64]`) seeds:
   ```
   HKCU,Software\Valve\Steam,"SteamPath",,"%16426%\Steam"
   HKCU,Software\Valve\Steam\ActiveProcess,"SteamClientDll",,"%16426%\Steam\steamclient.dll"
   HKCU,Software\Valve\Steam\ActiveProcess,"SteamClientDll64",,"%16426%\Steam\steamclient64.dll"
   HKCU,Software\Valve\Steam\ActiveProcess,"SteamPath",,"%16426%\Steam"
   HKCU,Software\Valve\Steam\ActiveProcess,"PID",0x10001,0x0000fffe
   ```
2. `steam.exe` (Proton's `steam_helper/steam.c`) overwrites `ActiveProcess\pid` with its real PID
   (`:64-69`), sets `SteamPath`/`ValvePlatformMutex` env vars, creates the `vguiPopupWindow` window
   and the `Steam3Master_SharedMemLock` / `Global\Valve_SteamIPC_Class` events (`:872-895`), then
   `LoadLibraryW(L"lsteamclient")` and calls its private `steamclient_init_registry` export
   (`:206-221`).
3. `steamclient_init_registry` (`unixlib.cpp:700-721`) runs on the **unix** side: it creates
   `SteamClient017`, opens a pipe and global user, and writes `Software\Valve\Steam\language`,
   `Software\Valve\Steam\Apps\<appid>\{Installed,Running,Updating}` etc. into the Wine registry via
   `NtCreateKey`.
4. The game's `steam_api64.dll` reads `ActiveProcess\SteamClientDll64`, `LoadLibrary`s
   `C:\Program Files\Steam\steamclient64.dll`, and `GetProcAddress`es `CreateInterface`,
   `Steam_BGetCallback`, `Steam_GetAPICallResult`, `Steam_FreeLastCallback`,
   `Steam_ReleaseThreadLocalMemory`. `SteamInternal_SteamAPI_Init` then checks the interface-version
   list at `steam_api.h:231-256` — 24 `*_INTERFACE_VERSION` strings, NUL-separated —
   which for SDK 165 includes `STEAMUSERSTATS_INTERFACE_VERSION013`.
5. Our `CreateInterface` (`steamclient_main.c:388-396`) calls `load_steamclient()` on first use,
   which forwards `SteamAppId` / `IgnoreChildProcesses` env vars and the temp path across the seam
   and triggers `steamclient_init` (`unixlib.cpp:723-791`): `dlopen` the native library, `dlsym` the
   seven flat entry points. Then, back on the PE side, `WSAStartup(0x202)` is called because "some
   games depend on winsocks being initialized after initializing Steam API" (`:376-383`).

> **Open question.** Proton's prefix gets `steamclient.dll` / `steamclient64.dll` copied from
> `<steamdir>/legacycompat/` (`proton:1078-1090`), while the actual implementation is Wine's builtin
> `lsteamclient.dll` — whose `.spec` reproduces `steamclient.dll`'s export set *with matching
> ordinals 1-57*. The exact linkage between the two filenames is not determinable from Proton's
> sources (the legacycompat binary is a Valve-shipped PE). For our port this is moot: we control the
> filename that `ActiveProcess\SteamClientDll64` points at, so we can point it straight at our own
> PE. **This needs to be settled experimentally before we write the bootstrap.**

### 7.2 The call sequence, and what must fire

Steamworks contract, from `steamworks_sdk_165/isteamuserstats.h`:

- `RequestCurrentStats()` is **commented out** at `:95` in SDK ≥ 143 or so — "this call is no longer
  required as it is managed by the Steam client". It is still a real vtable slot in older interface
  versions (`steamworks_sdk_128/isteamuserstats.h:92`, `steamworks_sdk_142:93`), and older games call
  it. On `STEAMUSERSTATS_INTERFACE_VERSION013` **it does not exist** — the vtable begins at `GetStat`.
- `SetAchievement(const char*)` (`:115`) — local, synchronous, returns `bool`. It does *not* talk to
  the server and fires no callback.
- `StoreStats()` (`:130`) — "Store the current data on the server, **will get a callback when set /
  And one callback for every new achievement**".

Callbacks (`isteamuserstats.h:327-357`, base `k_iSteamUserStatsCallbacks = 1100` from
`steam_api_internal.h:253`):

| Struct | id | Fires |
|---|---|---|
| `UserStatsReceived_t` | **1101** | after stats are available (in response to `RequestCurrentStats` on old interfaces; automatically at startup on new ones) |
| `UserStatsStored_t` | **1102** | once per successful `StoreStats()` |
| `UserAchievementStored_t` | **1103** | once **per newly unlocked achievement**, after `StoreStats()` |

Ordering: `1101` (once, before the game may meaningfully read/write stats) → …game calls
`SetAchievement` → `StoreStats` → `1103` for each newly unlocked achievement, and `1102` for the
store operation. `1102` and `1103` are both consequences of the same `StoreStats` round-trip;
`isteamuserstats.h:126-129` only guarantees that both arrive, not their relative order, so **do not
assume 1102 comes last**.

### 7.3 Why the achievement path is the easy one

Grepping the generated conversion table for these three ids returns **nothing**:

```
$ grep -n "{ 110[123]," unixlib_generated.cpp
$
```

`UserStatsStored_t` and `UserAchievementStored_t` are emitted **unprefixed** in
`steamclient_structs_generated.h` (`:2301-2355`), i.e. the generator classified them as *unique* —
identical layout across all of `u32`, `u64`, `w32`, `w64` and all 105 SDK versions. Only
`UserStatsReceived_t` is versioned, and only because a `CSteamID` field was *added* in SDK 102x
(`UserStatsReceived_t_099u`, 16 bytes → `UserStatsReceived_t_102x`, 24 bytes) — the two *layouts*
still agree across ABIs.

The reason is worth stating explicitly, because it is not obvious: `CSteamID` and `CGameID` are
declared inside `#pragma pack( push, 1 )` in `steamclientpublic.h:479`, so they have **alignment 1**
on every platform. That kills the only field in these three structs that could have introduced a
`pack(4)`/`pack(8)` divergence. Proton's `C_ASSERT`s pin it (`unixlib_generated.cpp:14858-14864`):

```c
C_ASSERT( sizeof(UserStatsReceived_t_102x) >= 24 );
C_ASSERT( offsetof(UserStatsReceived_t_102x, m_nGameID) == 0 );
C_ASSERT( offsetof(UserStatsReceived_t_102x, m_eResult) == 8 );
C_ASSERT( offsetof(UserStatsReceived_t_102x, m_steamIDUser) == 12 );
```

**Consequence: for a v1 achievement round-trip we need no struct converters at all — a `memcpy` for
callbacks 1101/1102/1103 is provably correct.**

## 9. Verdict: copy / rewrite / skip

**Copy essentially verbatim (design, and where licensing allows, code):**

- The `u_iface` opaque-64-bit-handle model (§2). This is the keystone.
- The `w_iface` = `{ vtable, u_iface }` two-field PE object.
- Declaring the native interface as a C++ class of pure virtuals and letting the compiler emit
  Itanium virtual dispatch (§2) — macOS uses the same ABI, so this works unchanged.
- The two-phase `Steam_BGetCallback` protocol (§6.1).
- The length-keyed `struct callback_def` table for resolving callback struct versions (§6.2).
- The `SteamAPICallCompleted_t` inner-length fixup.
- The `alloc_callback_wtou` "return the original pointer when no conversion is needed" trick.
- The explicit-padding + `C_ASSERT` discipline for every cross-ABI struct (§5.2).
- `IsBadStringPtrA` pre-touch on `const char *` params (§4.2).
- The deferred upcall queue design (§6.4) — for later, when we need
  `ISteamMatchmakingServers`/warning hooks.
- The `Set_SteamAPI_CCheckCallbackRegisteredInProcess` stub-returning-1 hack.

**Must rewrite:**

- The build. Proton's `rules-makedep.mk`/`makedep`/`Makefile.in` path requires a built Wine tree
  (§3.3). We build the PE with mingw-w64 and the unix side with clang, and hand-roll
  `__wine_unix_call_funcs[]`. Verified feasible in `crossover-bridge-surface.md`.
- Vtable emission. `__ASM_VTABLE`/`DEFINE_RTTI_DATA0` are Wine-internal x86 asm macros; on win64 we
  can emit a plain `static void *vtable[]` array plus a preceding RTTI locator slot. **Must preserve
  the MSVC reverse-overload-order rule** (§3.1).
- `WINE_DEFAULT_DEBUG_CHANNEL` / `TRACE` / `wine/list.h` / `wine/asm.h` — replace or vendor.
- The generator. `gen_wrapper.py` bakes in `CLANG_PATH='/usr/lib/clang/15'`,
  `-I/usr/include/x86_64-linux-gnu/`, 105 vendored SDKs and four-ABI parsing. For a small interface
  set, hand-writing is faster and more debuggable than adapting it. Revisit only if we need broad
  interface-version coverage.
- Anything wow64 (§1.4) — delete.

**Skip entirely:** i386/thiscall wrappers, aarch64/arm64ec, the `.data` allocation hack, X11 keycode
mapping, path conversion (v1), the Steam runtime container, `Steam_BGetCallback`'s overlay
`keybd_event` hack.

**Minimum viable achievement round-trip: 5 flat exports, 3 interfaces, ~20 real method bodies, one
`memcpy` callback path, zero struct converters.**

## 10. Open questions

1. **How does `steam_api64.dll` actually reach our PE?** Proton copies Valve's
   `legacycompat/steamclient64.dll` into the prefix while the implementation is builtin
   `lsteamclient.dll`; the linkage is invisible in Proton's sources (§7.1). Needs an experiment:
   point `ActiveProcess\SteamClientDll64` directly at our own DLL and see whether `steam_api64.dll`
   is happy, or whether it hard-codes the filename.
2. **Does the macOS `steamclient.dylib` export the same flat C entry points** (`CreateInterface`,
   `Steam_BGetCallback`, `Steam_GetAPICallResult`, `Steam_FreeLastCallback`,
   `Steam_ReleaseThreadLocalMemory`, `Steam_IsKnownInterface`, `Steam_NotifyMissingInterface`) that
   `unixlib.cpp:781-787` `dlsym`s? `CreateInterface` was confirmed present in the CrossOver research;
   the other six are unverified. This is a five-minute `nm -gU` check and it gates everything.
3. **Which `SteamClient0NN` version does the current macOS client vend**, and does
   `ConnectToGlobalUser` succeed from a Rosetta x86_64 process talking to an arm64 Steam client over
   Valve's IPC?
4. **Interface-version coverage.** `SteamInternal_SteamAPI_Init` validates 24 interface version
   strings (`steam_api.h:231-256`) but the exact failure mode when one is unavailable is unclear —
   does it hard-fail, or does it only fail on `SteamInternal_FindOrCreateUserInterface`? Determines
