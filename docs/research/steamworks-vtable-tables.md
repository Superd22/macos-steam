# Steamworks interface vtable tables — the authoritative slot order

**Why this exists.** The shim presents MSVC vtables to `steam_api64.dll`. A wrong
vtable index does not error: it corrupts the call and segfaults, and under Wine a
fault looks exactly like a hang (#11). Before this document, shim slots were
discovered one crash at a time. This is the whole table, up front.

## Source of truth

Proton's `lsteamclient` **PE-side** generated files, one per interface:
`https://github.com/ValveSoftware/Proton/tree/proton_11.0/lsteamclient/winISteam<Iface>.c`

Each contains, per interface version, an `__ASM_BLOCK_BEGIN(win<Iface>_<VER>_vtables)`
block listing `VTABLE_ADD_FUNC(...)` in **exact vtable order**, and a matching
`alloc_vtable(&..., <N>, ...)` giving the slot count as an independent cross-check.
These files are generated by clang from Valve's own SDK headers, so they already
encode the MSVC same-name-overload reversal — which is why they, and not the
headers, are what the PE side must match.

## The trap: do NOT use the `cpp*.cpp` files

The unix-side `cppISteamUtils_SteamUtils010.cpp` lists forwarding thunks, and it
**omits methods Proton handles manually** — `GetAPICallResult` is missing from
`SteamUtils010`. Extracting order from it shifts every slot from 13 onward down by
one, putting `GetSteamUILanguage` at 22 instead of 23. Silent, and exactly the
failure mode above. Always use the `win*.c` vtable block.

## Extraction

```sh
gh api "repos/ValveSoftware/Proton/contents/lsteamclient/winISteamUtils.c?ref=proton_11.0" \
  --jq '.content' | base64 -d > winISteamUtils.c
# then read the __ASM_BLOCK_BEGIN(winISteamUtils_SteamUtils010_vtables) block in order
```

## Overload groups

Proton disambiguates same-name overloads with a `_2` suffix, and MSVC orders them
in **reverse** declaration order — so `GetStat_2` precedes `GetStat`. In
`STEAMUSERSTATS_INTERFACE_VERSION012` these are slots 1/2 (`GetStat`), 3/4
(`SetStat`), 17/18 (`GetUserStat`), 39/40, 41/42, 43/44. The native (Itanium)
class in `steam_ifaces.h` uses plain declaration order, so only the slot COUNT of
an overload block matters there — which is why the two files legitimately differ.

## Tables

Verified against the shim's existing wiring: `SteamClient020` slots 0,1,2,4,5,8,9,
12,13,15; `STEAMUSERSTATS_INTERFACE_VERSION012` slots 0,6,7,8,9,10,12,14,15,21;
`SteamUtils010` slot 9; `STEAMAPPS_INTERFACE_VERSION008` slots 0-9 — all correct.
